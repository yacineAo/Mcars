# 25 — OwnerInstallment (Payments)

**Model:** `App\Models\OwnerInstallment` · **Slug:** `/admin/owner-installments` · **Status:** 🟡 partial

Closes **ADV-07** (owner payouts). Read
[`../05-accounting-model.md`](../05-accounting-model.md) — posting **E32** is the monthly
accrual, and the owner payable is account **2200**.

## What it is for

What the business owes each car owner. Mcars runs owned and managed cars side by side; a managed
car earns its owner a monthly rent, accrued into account 2200 and paid out later. This screen is
where the accountant accrues the month and sees what is outstanding.

`accrue` is correctly built: it delegates to `PaymentService::accrueOwnerInstallment()` and is
`visible()` only while `! $record->isPostedToLedger()`
(`OwnerInstallmentResource.php:71-85`), so it cannot double-post through the UI.

Confirmed good: `owner_installments` has **no `amount_paid` column** — CLAUDE.md bans it
explicitly, and the paid figure is derived in `ReportService::ownerStatement()` via
`installmentPaidAmount()`, which sums ledger rows against account 2200. The invariant holds.

## Should be

### Index
Extend the filters with: **unaccrued** (`accrual_transaction_id IS NULL`) — the accountant's
month-end queue and the reason `accrue` exists; overdue by `due_date`; `period_month`; owner;
and car.

Columns: owner, car, `period_month`, `due_date`, `amount_due`, status, accrued indicator, and a
derived **paid** figure from `ReportService::ownerStatement()`, gated. Today whether an
instalment has been accrued is only visible from the action still being offered.

### Create
Instalments should be generated by `OwnerStatementService`, not typed. Manual creation should
stay available for corrections but is not the main path.

### View
Worth adding: the owner and car as links, the period and amount, the accrual posting, and any
payments made against it — the single-instalment version of the owner statement report.

### Edit
**Freeze once accrued.** `amount_due`, `period_month` and the owner/car must become read-only
once `accrual_transaction_id` is set: posting E32 has already credited 2200 with that figure, so
editing it afterwards makes the payable disagree with the ledger. Notes and `waived_reason` only.

see the Fleet audit for that resource.

## Gaps and risks

1. **🔴 No `canAccess()`.** This screen creates a liability to a third party and posts it to the
   ledger. Anyone can currently accrue, edit and bulk-delete. `DepositResource` in the same
   group is gated on `reports.view_financials`; this should be at least as tight.
2. **🔴 `DeleteBulkAction` on accrued instalments.** Deleting an instalment leaves its E32
   posting crediting 2200 with nothing behind it, so the owner statement and the balance sheet
   disagree permanently.
3. **🔴 Nothing frozen after accrual** — see Edit. Same pattern as
   [`22-payment.md`](22-payment.md) gap 3 and [`15-expense.md`](15-expense.md) gap 6; worth
   fixing as one sweep across the money resources.
4. **🟡 `total_installments` is hardcoded to `999`** at `OwnerStatementService.php:66`. Owner
   rent is an open-ended monthly accrual, so there is no real instalment count — but the column
   implies one, and 999 is a placeholder standing in for "indefinite". Either drop the column
   or make the sentinel explicit (nullable, meaning open-ended) so a report never prints
   "3 of 999".
5. **🟡 No unaccrued filter** despite an action existing to clear that queue.
6. **🟡 No accrued indicator column.**
7. **🟡 No derived paid figure**, though `ReportService` already computes it.
8. **🟡 Deprecated `->actions([...])`.**
