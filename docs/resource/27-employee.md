# 27 — Employee (HR)

**Model:** `App\Models\Employee` · **Slug:** `/admin/employees` · **Status:** ✅ done

Supports **ADV-07**. See [`../tasks/phase-06-payments-deposits.md`](../tasks/phase-06-payments-deposits.md).

## What it is for

Staff records: who works here, their job, their hire date and their base salary. Referenced by
payroll, commissions and advances, and by bookings via `driver_employee_id` when a car goes out
with a driver.

## Should be

### Index
Shows employee number, name, job title, department, hire date and active status. **Not base
salary** — the index deliberately has no salary column, so a supervisor who may read the
directory never sees what anyone earns. Filter by department, job title and status, the two
text filters deriving their options from the rows the user can actually reach (branch-pinned
`distinct` queries), not a fixed list.

### Create
`employee_number` is generated by `EmployeeService` through `SequenceGenerator` — which **must
run inside a transaction or it throws** — in the same transaction as the insert, so a rolled-back
employee takes its number back with it (`EMP-MAIN-2026-000001`). The create form has no number
field at all, and the edit form shows it disabled with the record's own value re-asserted in
`mutateFormDataBeforeSave()` against a crafted payload.

### View
The reason to open the record: identity, employment and contact sections, then a **salary
section that only renders for `hr.view_salary`** (base_salary, salary_type), then the three pay
histories behind the same gate. A supervisor's view page shows no salary anywhere.

### Edit
Manager-only (`hr.manage`). `base_salary` changes are **not effective-dated** — the decision was
to keep the run history in the payroll items (a historical run is explained from its own
numbers) and record the salary change itself in the activity log: `Employee` uses `LogsActivity`,
which logs every dirty attribute, so who changed the salary and to what is on record.

### Relations

| Relation | Where | Read-only | Gate | Columns |
|---|---|---|---|---|
| `payrollItems` | view | yes | `hr.view_salary` | run period, base, commissions, advances recovered, net |
| `advances` | view | yes | `hr.view_salary` | advanced on, amount, status, recovered in (run period) |
| `commissions` | view | yes | `hr.view_salary` | earned on, booking, basis, rate, amount, status |

All three expose pay, so all three sit behind the same gate as the salary field. "One employee's
own record showing their own pay is fine; one employee seeing another's is not" is enforced by
restricting who may read pay at all — the pay relations exist only for `hr.view_salary` roles,
and `canViewForRecord` is the same check as the salary section's `visible()`.

### Actions

| Action | Placement | Visible when | Guarded by | Delegates to | Notes |
|---|---|---|---|---|---|
| `EditAction` | row | always | `hr.manage` + branch reach | — | the only row action |
| `CreateAction` | toolbar | always | `hr.manage` (`canCreate`) | `EmployeeService::create` | numbers via `SequenceGenerator` |
| _(none)_ | toolbar | — | — | — | **no bulk actions** — there is no delete path at all |

## Gaps and risks

1. **`base_salary` unprotected — fixed.** `canAccess()` now requires `hr.view`, and a new
   permission `hr.view_salary` (super_admin, manager, accountant) gates the salary field, the
   view-page salary section and all three pay relation managers. `reports.view_financials` was
   deliberately not reused: this is payroll confidentiality, not financial reporting. A third
   permission, `hr.manage` (super_admin, manager), gates create/edit — the visibility matrix's
   "full". All three are seeded in `RolePermissionSeeder`; an unseeded permission would silently
   deny everyone (finding 8).
2. **`DeleteBulkAction` — removed.** No delete path of any kind (`canDelete()` returns false):
   employees are master data that payroll items, commissions, advances and bookings reference.
   An employee leaves by a status change — the status select drives `active` → `terminated`.
3. **No row actions — fixed.** Explicit `EditAction`, gated on `hr.manage`.
4. **No view page — fixed.** `ViewEmployee` with the three gated, read-only relation managers.
5. **`base_salary` overwritten rather than effective-dated — accepted, see Edit.** The history of
   a payroll run lives in the payroll items; the change itself is recorded by `LogsActivity`.
6. **`employee_number` typed rather than generated — fixed.** `SequenceGenerator` inside the
   same transaction as the insert (see Create).

## Verification

```bash
docker compose exec app ./vendor/bin/pest tests/Feature/EmployeeResourceTest.php
docker compose exec app ./vendor/bin/pest tests/Feature/Phase6Test.php
docker compose exec app ./vendor/bin/pest tests/Feature/PanelAccessTest.php
docker compose exec app ./vendor/bin/pest tests/Unit/SequenceGuardTest.php
```

`EmployeeResourceTest` (13 tests) covers the three access gates (receptionist and maintenance
are refused the resource; a supervisor reads the directory with no salary column and no pay
relations; the accountant reads salaries but never edits), the crafted-create refusal, number
generation through the sequence (format `EMP-MAIN-\d{4}-\d{6}`, unique and gap-free), the number's
immutability against a crafted edit payload, the absence of every delete path, a departure
recorded as a status change, the department filter, fail-closed branch pinning on the list and
the record pages (a cross-branch record 404s — its existence is not leaked), and the view page
rendering all three pay histories.

`SequenceGuardTest` lives in `tests/Unit` because it asserts behaviour at transaction level 0 —
`EmployeeService::create` wraps its `SequenceGenerator` call in `DB::transaction`, so the guard
still proves the generator throws when a future caller forgets the transaction.

By hand: open the resource as a receptionist (refused), as a supervisor (directory, no salary
anywhere), then as a manager (full record, generated number, pay histories on the view page).
